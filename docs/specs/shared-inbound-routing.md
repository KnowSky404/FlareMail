# PRE 与 PROD 的收信归属 SPEC

在 [固定 PRE 地址方案](single-worker-pre-inbound.md)的基础上，两个环境通过自己的邮箱设置管理收信。不同域名可以分别收信。同一个域名可以在 PRE 和 PROD 配置不同邮箱，同一个邮箱和同一个域名的 catch-all 各有唯一归属。

## 数据和配置

生产 Worker 继续接收 Cloudflare Email Routing 交付的邮件。生产和 PRE 各自保有 D1 和 R2，包括 Owner、邮件身份、原信、正文、附件和处理状态。共享的归属 D1 只保存规则类型、归属键和目标环境。两个环境的应用都绑定这套归属 D1。生产 Worker 额外绑定 PRE 邮件 D1/R2，入站分流选中 PRE 后才访问这套邮件存储。现有模板省略共享配置时，普通生产入站和本地的固定 PRE 地址模式沿用原有语义。

共享归属目标 `inboundRouting` 声明 D1 ID、名称和环境角色。生产目标配置 `preInbound` 和明确的 `PRE_INBOUND_ENABLED`。原生 PRE 目标只配置自己的主 D1/R2 和共享归属 D1。归属库与所有邮件库使用不同的 D1 ID。三套存储均使用私有目标配置。

## 归属和交付

| 类型 | 归属键 | 规则 |
| --- | --- | --- |
| 邮箱 | 小写基础地址 | 精确地址与基于它的 `+tag` 属于同一环境。同域名的不同基础地址可独立配置。 |
| catch-all | 小写完整收信域名 | 一个域名仅有一处归属，已登记的邮箱始终优先。 |

生产 `email()` 根据 SMTP 信封收件地址查一次归属，优先匹配基础地址，再匹配完整域名的 catch-all。选定后由对应邮件库验证 Owner、是否启用、地址和 catch-all 的现有规则。邮箱归属要求实际命中托管身份，catch-all 归属要求实际命中未知地址收集。归属缺失或与本地身份状态不一致时拒收。归属库不可用时中止本次处理。生产邮件不访问 PRE 邮件库，PRE 写入失败结束本次交付。PRE 投递沿用固定模式的副作用限制。

旧固定 PRE 保留地址可在两个目标的 `vars.PRE_INBOUND_RECIPIENT` 中同时声明。生产 Worker 优先应用原有分流逻辑，并在共享模式下确认邮箱归属 PRE 后才投递。PRE 允许管理精确地址，两边都阻止为该地址创建 `+tag` 规则。回填校验两个目标的保留地址一致，并将该地址族登记为 PRE 归属。普通模式的子地址规则、已删除记录和 catch-all 健康检查沿用当前实现。

## 互斥和变更

- 新增邮箱和启用 catch-all 在写入本地身份或平台规则前申请归属。数据库唯一约束裁定并发。相同环境重试可重复申请，另一环境收到冲突。
- 创建、同步、启停、恢复、检查路由、删除和重试不能接管另一环境的归属。同步只导入已分配给本环境的规则，管理员先通过明确的配置操作取得归属。两边可以各自登记同一域名。
- 域名检查与定时刷新核对已开启收集的 catch-all 归属，分别显示未登记归属和归属另一环境。
- 身份发现和批量健康检查在归属库批量查询候选邮箱，再按当前环境过滤。
- 停用、删除、关闭收信和创建中途失败均保留归属。重试可补齐本地身份。移交归属涉及停止接收、排空和核对规则，作为独立的运维操作处理。
- 停用域名时可保留其收集选项，停用请求无需取得新的 catch-all 归属。从拒收切换到收集仍须核对平台规则。重新启用收集时会校验归属。
- 云端规则仍需把邮件交给生产 Worker。对共享域名的规则变更只授权本环境拥有的精确地址；域名 catch-all 单独授权。核对 Dashboard 和其他会绕过应用的配置入口。

## 兼容切换

先盘点两边所有邮箱记录，包括已停用和已删除记录、固定 PRE 地址以及登记的 catch-all。生成只读冲突清单，对相同基础地址或同一 catch-all 的重复归属先处理冲突。初始化归属库时可重跑，重复执行不能改写已有归属。迁移只写归属记录，历史邮件和对象保留在原库。

切换前暂停并排空两边的身份写入及旧版在途规则操作。用同一批数据核对生产与 PRE 实际使用的归属 D1 和两套邮件资源。已生效的 PRE 归属在停收及回退期间继续阻挡生产 catch-all。只在通过旧版本入口、绑定、初始映射以及真实收信验收门禁后进行远程切换。发布前的 PRE 网页验收与生产 SMTP 验收分开记录。

## 实施和验收

先实现本地归属迁移、双环境配置互斥和 Worker 分流。使用三套隔离本地 D1 及两套 R2 验证两个域、共享域、重复申请、显式地址覆盖 catch-all、停用/删除、未知地址、PRE 停收和故障隔离。保留固定模式和未配置场景的回归。

发布脚本和原生远程构建继续禁止带新归属绑定的发布。带 PRE 入站配置的本地 Worker 使用 `cf dev`，构建命令拒绝生成可上传的 Worker 产物。批量登记和冲突检查先在本地使用，实际部署绑定预检、回退验证和真实 SMTP 切换在获得相应授权后单独完成。

### 本地运行

从 `cloudflare.local.json` 派生两个本地目标，使用同一个隔离的 `FLAREMAIL_STATE_DIR`。生产目标的 `vars.PRE_INBOUND_ENABLED` 使用字符串 `"true"` 或 `"false"`，`preInbound` 使用 PRE 目标的主 D1 ID、名称和桶名。两份目标使用下面同一份 `inboundRouting` 资源配置，分别将 `environment` 设为 `"production"` 和 `"preview"`。

```json
{
  "inboundRouting": {
    "databaseId": "00000000-0000-4000-8000-000000000003",
    "databaseName": "flaremail-routing-local",
    "environment": "production"
  }
}
```

分别对两个目标运行 `bun run db:migrate:local`。选择生产目标运行 `bun run db:migrate:local -- --inbound-routing` 初始化共享归属库。对已有身份先运行 `bun run mail:routing:backfill -- --production <PROD 本地目标> --preview <PRE 本地目标>`。冲突报告包含规则类型及 `JSON.stringify([kind, key])` 的 SHA-256，供在本地核对已知地址。存在冲突时退出码非零，归属库保持原样。停住两边的本地身份写入并核对目标后，加 `--apply` 写入共享归属库。邮箱和域名设置使用各自选定的本地目标，模拟收信使用生产目标运行 `bun run preview`。
