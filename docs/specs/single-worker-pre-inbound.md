# 单 Worker 的 PRE 真实收信 SPEC

设计基线为 `f020e6b0ed5918eccae6e555f9c9c41da19c3c25`，状态为待实现。FlareMail 面向个人自托管，每套环境各有一个 Owner。此次整改让生产和 PRE 共用一个入站 Worker，同时保持各自的邮箱、原文和附件存储。

独立 PRE 收信 Worker 的试验已结束。Cloudflare 在删除该 Worker 时禁用了它原来的一条精确规则，原生 PRE 网页和隔离存储继续保留。PRE 的邮箱记录及邮件身份目标配置仍可能引用旧规则或旧 Worker。切换时要核对 Cloudflare 实际状态并重新关联。

旧地址仍可能命中生产 catch-all。撤下时检查了生产 D1，旧地址所属域名未配置，现有处理器会按未知域名拒收。生产身份或规则之后可能变化，所以本项目首次切换必须将原 PRE 测试地址本身作为保留地址，覆盖其子地址。若原地址出现冲突，先暂停切换，轮换按下文的持续隔离条件另行处理。真实验收在该地址启用分流且精确规则和两套绑定核对通过后执行。

## 平台边界与方案

生产 `flaremail` 是 Cloudflare Email Routing 的 Worker 目标。原生 Preview `mail-ai` 提供独立的 HTTP 地址、变量和绑定。精确地址规则和 catch-all 都调用目标 Worker 的生产 `email()`。因此，给 PRE 配置独立的 D1 和 R2 后，邮件仍需在生产的入站入口分流。依据见 [Email Routing 规则](https://developers.cloudflare.com/email-service/configuration/email-routing-addresses/)、[Email Worker API](https://developers.cloudflare.com/email-service/api/route-emails/email-handler/)和 [Preview 资源与限制](https://developers.cloudflare.com/workers/previews/resources/#limitations)。

| 做法 | 收信行为 | 代价 |
| --- | --- | --- |
| 生产入口按 SMTP 收件地址分流 | 同一个 `email()` 使用选中的 D1 和 R2，PRE 网页读取自己的存储 | 生产入站入口需要绑定 PRE 存储，变更随生产代码发布 |
| 生产入口通过 HTTP 转交 PRE 网页 | PRE 的网页版本可以处理原始 MIME | 需要新增 Web 接收端、服务身份鉴权、体积限制、幂等和跨请求失败处理 |
| PRE 与生产共用 D1 和 R2 | PRE 网页能看到生产邮件 | 邮件、状态和写操作跨环境共享 |
| 为 PRE 单独部署收信 Worker | 可独立发布 PRE 的 `email()` | 增加一个 Worker 和一套发布维护流程 |

采用第一种做法。首期支持一个管理员配置的 PRE 地址，继续使用原生 `mail-ai`。这能用新版本的 PRE 网页验收阅读和设置，用生产部署的收信代码验证真实 SMTP 投递。新 `email()` 代码的发布前依据是两套隔离本地存储的测试。

## 入站分流

在 `worker/index.ts` 的 `email()` 入口选择存储，然后复用现有 `handleInboundEmail`。判断依据是 Cloudflare 的 SMTP 信封收件地址 `message.to`，沿用现有收件地址的去空白、小写和格式校验。邮件 `To`、`Cc`、`Delivered-To`、自定义头和正文均没有环境选择权限。原始 MIME 只读一次，保存时保留真实信封地址。

1. 正式启用前，在私有生产目标和原生 PRE HTTP 目标配置相同的完整 `PRE_INBOUND_RECIPIENT`。配置值使用 `normalizeManagedAddress` 按已登记的 PRE 域名校验，额外要求完整邮箱和无 `+` 的 local part。收信事件仍使用原有信封校验。生产入站以该保留地址为最高优先级，PRE 网页以同一保留地址限定可核验的身份范围。
2. 生产使用 `PRE_INBOUND_ENABLED` 控制交付。启用时接收完整普通地址，停用时明确拒收该地址。此地址的 `+tag` 变体始终拒收，避免继承生产身份或进入 catch-all 收集。
3. 其他收件地址走现有生产解析，继续遵守生产的显式地址、子地址、删除记录和未知地址策略。运行时判定与生产、PRE 数据库的查询结果保持独立。
4. PRE 路径要求 `PRE_INBOUND_DB` 与 `PRE_INBOUND_BUCKET` 同时可用。缺少绑定、Owner 或启用的精确身份时，按现有入站语义报错或拒收。从分流开始只使用一次选定的存储组合，任何 PRE 失败都结束本次处理。

生产配置只允许三种状态。已经建立保留地址的环境通过显式开关跨状态切换。

| 状态 | 生产配置 | 收信行为 |
| --- | --- | --- |
| 从未启用该功能的实例 | 地址、开关和 PRE 存储绑定均未声明 | 使用现有生产解析 |
| 已保留，暂停交付 | 合法地址、显式 `false` 和两个 PRE 绑定 | 拒收保留地址及其子地址 |
| 已保留，启用交付 | 合法地址、显式 `true` 和两个 PRE 绑定 | 精确地址写入 PRE，子地址拒收 |

只要声明其中任一配置项，打包和运行时就按整套配置校验，部分缺失、开关非法或地址非法均为配置错误。部署应在切流量前失败。运行时遇到非法组合时，入站调用明确失败，禁止走生产默认分流。发布前对照当前激活的保留地址、两个目标、实际部署和已保存的身份。普通发布和暂停交付都要保留已备案的地址。首期固定使用该地址，地址退役或轮换只有在旧地址及其子地址已有持续隔离机制时才可以另行实施。

生产发布预检必须从当前活动 Worker 版本绑定和已有的私有发布记录核对保留状态。已备案的地址缺失或与候选目标不同，预检即失败，包括旧配置同时省略四项 PRE 设置的情形。无法验证当前状态时停在预检，生产路由是否启用或 Cloudflare 精确规则是否存在均不作为绕过依据。该检查只记录匹配结论。

生产建立保留地址后，每次 PRE 发布也须把候选地址、D1 和 R2 与当前生产活动版本的 PRE 入站绑定及私有记录逐项比较。地址或任一存储缺失、不同或无法核对时停在上传前；仅已暂停并排空的授权换绑窗口可暂时使用不同存储。生产发布按同样方式把候选入站配置与当前 PRE 实际部署比较。两个方向都须在发布后核对实际部署再验收。首次生产保留尚未建立时，PRE 可按经核对的私有发布计划做 HTTP 验收，真实投递仍等待完整切换。

紧急暂停收信允许在 PRE 绑定漂移或 PRE 元数据暂时不可读时执行。先核对生产活动配置及私有保留记录，复用验证过的生产守卫代码和相同资源绑定、地址及其他配置，发布将交付开关设为 `false` 的新 Worker 版本。随后核对生产活动版本已全量执行拒收保护。后续修复与恢复仍须通过两侧对比及排空要求。

部署生效与预检使用同一个串行发布窗口。一个操作者在该窗口内负责两个环境的激活、回退以及相关路由变更，暂停可能同时发布的自动任务和仪表盘操作。激活前再次读取两侧活动版本与保留记录。只有满足上段条件的紧急暂停可以在 PRE 元数据不可读或漂移时激活，生产活动版本和保留记录仍要复核。预检基线变动时丢弃旧结果，按最新基线重跑预检。首个保留版本启用前，还要确认早于该版本、已上传但尚未激活的候选均已退出发布计划。构建可以提前完成，每次激活都须满足当前基线。首期通过现有授权窗口串行执行。

## 存储与权限

| 调用入口 | D1、R2 | 外部动作 |
| --- | --- | --- |
| 生产 `fetch()` 和 `scheduled()` | 生产 `DB`、`BUCKET` | 现有登录、邮件和计划任务 |
| 生产 `email()` 的生产分支 | 生产 `DB`、`BUCKET` | 现有生产策略 |
| 生产 `email()` 的 PRE 分支 | `PRE_INBOUND_DB`、`PRE_INBOUND_BUCKET` | 仅保存和索引；跳过自动回复、邮件通知、Telegram 和自动 AI 队列 |
| 原生 PRE `fetch()` | 同一套 PRE 资源，仍命名为 `DB`、`BUCKET` | PRE Owner 登录和查看；实际外部操作沿用独立授权 |

在 `cloudflare.config.ts`、部署目标解析和生成的 Worker 类型中声明两个可选绑定。私有配置填写真实资源，公开模板只提供占位和可选字段。每次部署校验生产与 PRE D1 ID、R2 桶名各自不同。正常部署和启用收信前，生产的 PRE 绑定还须与原生 PRE HTTP 实际绑定一致。两套 D1 的 schema 须与各自的入站版本兼容。生产和 PRE 的 Owner 映射由各自 D1 解析，依旧采用当前单 Owner 模型。

启用真实投递后，PRE D1 在线迁移要求线上生产 `email()`、所有可访问 PRE 存储的已部署入口和目标 PRE 网页版本均兼容迁移前后的 schema。清点包括原生 PRE 的稳定与部署专属 URL、版本预览 URL 和使用该存储的运维任务。任一入口不兼容时，先发布兼容版本，或在授权维护窗口暂停受影响的邮件、网页和运维请求。恢复的每个入口都须支持目标 schema。

暂停邮件交付时先确认生产 100% 使用拒收保留地址的版本。维护窗口须阻止已清点入口上的新请求，包括仍能访问同一存储的旧版本 URL，并等待已经进入的调用及其 D1/R2 操作结束。排空依据须包含可核对的调用结束记录或已验证的运行期限上限，抽样日志、一次拒收或不存在 processing claim 均不足以证明排空。无法确认时保持原绑定，仅执行所有服务版本均兼容的迁移。

首期沿用已有 PRE 存储。未来如需更换资源，在维护窗口执行独立授权的数据迁移。更换 D1 须迁移及验证现有 Owner、身份、邮件、草稿、设置、去重状态和其他业务记录，验证新库与旧库的保留数据一致。更换 R2 须核对 D1 的全部对象引用，包括原始 `.eml`、独立的完整纯文本和 HTML 正文、草稿、附件和待处理引用。用已有的大小及校验和字段验证对象，再实测阅读和下载。

已确认邮件、网页和相关任务暂停并排空时，两次发布之间允许暂时使用不同的 PRE 绑定。期间生产开关保持 `false`，两个目标仍分别校验其 PRE 资源与生产资源不同。恢复前逐个核对生产入站和所有本应使用 `mail-ai` 数据的入口及任务，要求版本、地址、实际 D1/R2 绑定及权限与选定的 PRE 存储一致。旧绑定或旧 schema 的入口继续关闭。使用独立测试存储的版本预览按其自身目标核对隔离，仍与 `mail-ai` 分开。

两套环境共用核心 MIME 解析、大小限制、claim 去重、事务、原文、正文、附件和 R2 回退逻辑。建议把已选中的存储和入站副作用策略明确传给处理器，PRE 的上下文只含自己的存储和入站限制。生产的 provider secrets 只供原有生产分支。当前 AI 入队直接读取 D1 的 Owner 偏好，首期需在入队处明确受分支策略约束。PRE 失败只影响本次 PRE 投递，生产的计划任务和 HTTP 数据访问仍使用各自原有入口。

生产部署进程具有读写 PRE 存储的能力，因此这里的隔离由绑定配置和应用代码共同保证。分流日志仅记录环境、结果、相关 ID 和阶段，避免记录完整邮箱、主题、正文、密钥或对象键。沿用现有 claim 的成功边界，确认持久化才视为成功。Cloudflare 对 Worker 异常的重投行为仍需通过受控 SMTP 验收确认。参见 [收信可靠性 SPEC](inbound-delivery-reliability.md)和 [Cloudflare 投递生命周期](https://developers.cloudflare.com/email-service/concepts/email-lifecycle/)。

## 邮件规则和身份管理

- 管理员核对生产 D1 存在的精确、基础和 `+tag` 身份、目标 Zone 的精确规则及 catch-all，保留一个只用于 PRE 的收件地址。若生产已有冲突身份、第三方规则或依赖，先解决归属再切换。
- Cloudflare 中该地址使用一条精确规则，指向生产 `flaremail`。生产 catch-all 继续作为其他地址原有的兜底。相同 Worker 名称只是平台目标，应用内的分流由保留地址控制。
- 原生 PRE 保留已保存的地址记录。在确认目标后，通过已授权的 PRE 数据操作把保留地址所属域名的 `mail_domains.worker_name` 更新为 `flaremail`，并按实际路由关联同一地址的规则 ID、来源和状态，域名保持未知地址拒收。PRE 的身份配置使用只读 Token，仅核验登记的 PRE 地址。首期关闭 PRE 的全量发现、规则写入和管理 Token。具体控制在服务端强制，网页按钮使用同一能力状态。
- 生产侧的同步、创建、恢复、启停、编辑、删除，以及它们的重试和检查修复均使用同一保留地址判断，覆盖 `+tag` 变体。批量同步跳过这些地址，单地址管理在改动 D1 或 Cloudflare 前拒绝。删除入口须保护相同地址的旧记录和已关联规则，包括此前由 FlareMail 管理的规则。部署或运行中的跨环境冲突应给出可诊断错误。配置的地址值通过私有目标维护。
- PRE 的身份健康检查先比较本地身份地址与配置的保留地址，再核验该地址的精确规则。缺少保留配置、记录地址不一致或规则禁用时均报告未匹配。即使生产 catch-all 的 Worker 名称相同，PRE 仍按外部兜底处理。首期 `MailIdentityManager.svelte` 将匹配显示为「精确规则已匹配」。PRE 页缺少生产开关的实时视图，因此对任何匹配结果均省略「收信已就绪」状态。实际入箱由授权的 SMTP 测试独立确认。
- 先覆盖全量同步、手动域名检查、刷新和后台健康检查，再在原生 PRE 启用只读 Token。健康检查统一先从 PRE 的保留地址解析唯一允许核验的域名、Zone 和身份。其余记录只读本地状态，禁止为它们访问 Cloudflare 或写回路由结果。平台查询返回的其他规则在服务端丢弃。

## 发布、切换和回退

1. 本地用独立的生产与 PRE D1/R2 执行同一 `email()` 流程。在原生 PRE 验收 HTTP、登录、收件箱和原文读取。记录实际绑定、应用 schema、路由基线和生产版本。私有目标及已部署环境的保留地址值应在发布前后安全比对，证据只记匹配结果。
2. 进入已授权的单地址切换窗口后，先暂停可能改动保留地址或所属域名的身份与规则操作，包括两侧网页管理、自动修复和仪表盘变更。确认旧身份写入、规则写入及操作租约都已结束，不确定结果通过目标 D1 和 Cloudflare 状态核实。在激活首个守卫之前重新核对生产 D1、精确及子地址规则和兜底策略，确认当前没有可收信的生产身份或接收路径。发现冲突时停止切换。该操作暂停持续到保护与规则更新验收完成。
   发布带保留地址拒收和双绑定校验的版本，保持收信开关关闭。确认生产 100% 运行含拒收保护的版本，未带保护的旧版本退出活动部署，且旧版处理该地址的在途调用已结束。核对生产目标、两个环境的存储指向和运行时健康状态。任一条件未通过时保留当前精确规则状态。
   切换前还要盘点可访问生产 D1 或规则管理权限的独立 URL，包括未承载常规生产流量的旧 Worker 版本 URL。所有仍可接入生产身份或规则管理的入口须使用同一保留地址守卫。不能满足时，先按授权关闭不具备守卫的入口。入口隔离也适用于后续发布和回退。
3. 继续在同一切换窗口内确认新守卫覆盖生产管理请求，并再次核对生产 D1 的精确、基础与显式子地址冲突、两侧绑定和 Cloudflare 规则。全部通过才可改动精确规则。核对前次规则的 ID、收件地址和来源，只更新已确认的规则，确实缺失时才新建。保持停收并复核 Cloudflare 目标与状态，以及 PRE 域名、规则 ID、Owner 和地址状态。
   启用前用获准的 SMTP 探测核对 Cloudflare 活动日志匹配的是该精确规则，并确认守卫拒收且两侧无存储写入。观察仍匹配 catch-all 或规则证据不足时继续停收。精确规则生效证据是切换门禁。运行时按信封地址分流，因为同一 Worker 的调用可以来自精确规则或 catch-all。
   门禁通过后启用 PRE 分支，确认启用版本接管 100% 的生产部署，再进行入箱验证。发现配置漂移或冲突时保持停收。
4. 验收要求 PRE 收件箱出现测试消息，原始 `.eml` 可下载，生产 D1 和 R2 对该次投递没有写入。另需验证正常生产地址仍交付到生产、未启用 PRE 时只拒收它的保留地址。
5. 回退版本必须保留同一地址及其所有 `+tag` 变体的拒收保护，部署时将 PRE 开关设为 `false`。提前验证含守卫的回退版本，再启用真收信。Cloudflare 删除或禁用精确规则后，邮件仍可能命中生产 catch-all。生产 D1 某时刻没有域名或身份，只能说明当时的行为，后续同步或收集策略修改可改变结果。需回退旧功能时，用包含相同守卫的兼容代码。回退保持 D1 schema、已收邮件和 R2 对象。参见 [PRE 指南](../PREVIEW.md)和 [生产发布清单](../PRODUCTION_CHECKLIST.md)。

## 实现验收清单

- 可持续交付的改动范围包括 Worker 入站选择、源于同一策略的邮箱身份防冲突、配置模板和类型生成，以及权限状态文案。
- 测试覆盖 SMTP 信封与头部冲突、大小写归一、完整地址和保留 `+tag` 拒收、生产子地址保持原语义、开关为真或假但地址缺失或无效、缺绑定、错误 Owner、地址禁用、存储失败和重投去重。发布前校验测试覆盖连续点、域名错配、旧配置省略全部 PRE 设置、候选地址被替换和无法核对活动版本。对两套存储记录、R2 对象及后续任务分别断言。
- 测试验证 PRE 邮件即使开启 Owner 的自动分类或通知偏好，也只保存邮件，不创建 AI 或 Telegram 队列，不触发生产回复或通知。生产正常处理和计划任务照常。
- 在本地和 PRE 验收身份管理：生产管理员不能接管保留地址或通过已有生产记录删除 PRE 规则，PRE 同步无法导入生产规则，过期身份地址和精确规则缺失报告未匹配。测试精确规则已启用而生产开关为 `false` 时，PRE 只显示规则匹配，生产入站确实拒收且没有写入。覆盖任一环境独立发布时误改地址、指向另一套独立存储或无法核对对侧活动版本的情况。生产 catch-all 不承担 PRE 地址健康。
- 验收切换顺序时模拟旧规则操作仍在途，以及旧同步在初检后写入生产冲突身份的情况。规则未排空或生产冲突复查失败时，阻止启用首个守卫和后续规则切换。
- 发布预检测试同时存在未保留地址的旧候选与首个保留版本的情况。保留版本激活后，旧候选即使已有预检记录也不能激活。
- 发布预检测试 PRE 配置漂移或暂时不可读时，仅允许保持当前地址和资源的紧急停收候选，普通发布、换绑和重新启用仍受双边核对。
- 发布验收应演练生产入站仍运行旧版本、现有 PRE 网页或版本预览尚未切换、暂停时已有邮件或网页请求在途的情况。确认不兼容入口及其旧调用停稳前，迁移或换绑不会继续。换绑过程中测试仅暂停状态允许临时不一致，生产资源始终独立；任一 PRE 入口恢复时重新要求一致。维护期间的暂停条件、拒收保护、排空和恢复各有独立结果。
- 串行执行仓库要求的 `bun run test`、`bun run check`、`bun run build`、`bun run cf:typegen` 和 `bun run deploy:dry-run`。在开发机核对全局 `cf` 与锁定的 Vite 插件兼容性，单独记录生产版本与真实投递证据。

换机后从包含本 SPEC 的最新 `origin/main` 创建实现 worktree。先构建和验证本地双存储用例，再按各环境授权使用各自的私有目标。真实资源标识和密钥继续通过私有配置及 Cloudflare Secret 管理。
