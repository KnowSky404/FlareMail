# 邮件摘要复用与 AI 自动分类 SPEC

状态：本地实现与 PRE 验收完成；PR 审查与生产发布分别执行。基线：`235c7e35f998ea3932d490a4539d51316a76583f`。

## 目标与实施顺序

1. 邮件打开后自动读取并展示有效的已有摘要；网页、专注阅读、独立阅读和 Telegram 共用一次分析。没有缓存时只展示明确的生成入口，不因打开邮件产生 AI 费用。支持手动重新生成、生成时间和失败后保留上次有效结果。
2. 用邮件用途重整分类，并在独立授权后对新入站邮件后台自动分类。复用现有 provider、D1、Cron、限额和分析缓存，不新增 SDK、云队列或资源。两个阶段在同一任务分支依次实现、验证。

## 分类契约

每封邮件一个主分类；现有自定义标签仍可多选，保持人工管理。

| ID | 中文 / English | 边界 |
| --- | --- | --- |
| primary | 主要往来 / Correspondence | 私人、工作讨论、明确需要人工回复的往来；无法判断的默认落点 |
| transactions | 交易账务 / Transactions | 订单、付款、账单、发票、退款、物流 |
| security | 账号安全 / Account security | 验证码、登录、密码重置、安全提醒；只是内容用途，不证明发件人可信 |
| updates | 服务通知 / Service notifications | 产品变更、系统状态、平台互动提醒 |
| subscriptions | 订阅资讯 / Subscriptions | 文章、新闻简报、社区周报、邮件列表资讯 |
| promotions | 营销推广 / Promotions | 促销、优惠、广告、销售触达 |

以主要目的决定类别；交易/安全正文不会因附带推广归为广告。内容规则优先于笼统发件地址，`noreply@` 只作最后兜底，`newsletter@` 不直接视作推广。论坛、社交平台按邮件内容进入相应分类。

旧 `social` / `forums` 归并到 `updates`，旧 URL/API 分类参数仍接受并规范化；已有人工选择迁移后仍标记为人工，不被 AI 覆盖。原始旧值留存于旧列，不能通过重新跑 AI 擅自改写。其他人工分类原样保留。新枚举使用新增列，避免重建邮件表和触发器。

分类优先级：人工覆盖 > 有效 AI 自动结果 > 本地发件人/标题规则 > primary。AI 自动值与人工覆盖分别保存。恢复自动分类清除人工覆盖并使用已有自动值/规则；人工修改与 AI 并发时以数据库写入条件保护人工选择。自动分类不移动文件夹、不归档、不删除、不标已读、不创建标签、不影响收发和安全隔离。

## 摘要读取与更新

- 阅读组件挂载/切换真实邮件 ID 或界面语言时仅 GET 缓存；有效结果默认展开。无缓存时仍提供手动生成按钮，POST 才允许供应商调用。
- 摘要、要点、待办、日期、分类建议共用结果；Telegram 只截取摘要展示，不保存另一份摘要。
- `summaryLanguage=auto` 统一采用保存设置时记录的工作区界面语言（旧设置默认 zh-CN）；浏览器切换语言不自动改写摘要输出语言。固定语言保持既有行为。旧客户端 language 参数保留校验，但不再造成网页/后台自动模式分叉。
- 正文、模型、endpoint、接口格式、输入上限、Prompt/Schema 版本变化仍使缓存失效；不能为复用而绕过正文完整性或权限校验。
- 显示成功生成时间；同一有效输入重新生成时保留旧结果，成功才替换，失败可刷新页面继续查看旧结果。失效结果不可当作有效缓存展示。
- 新分类 Prompt 升级分析版本，旧分析按现有机制失效；不会自动为历史邮件重新计费生成。

## 独立授权与后台处理

AI 设置新增默认关闭的 `automaticClassification`，文案明确有限正文会发往当前 AI 服务、消耗共享额度、只分析开启后的新邮件。与 Telegram 自动摘要分别授权；关闭 Telegram 不影响已授权分类，关闭全局 AI 停止新的调用。

服务端为一次连续授权保存不可伪造的 consent token；开启生成，关闭清除，再开启换 token。入站持久化事务尝试附带轻量 D1 工作记录，只给当时全局 AI 与自动分类均开启且未隔离的 owned mail 入队。可选工作入队失败时邮件仍须落库，记录脱敏错误；不扫描历史邮件补队。

Cron 增加独立任务，复用现有任务隔离模式。按租约领取有界批次，核对归属、当前授权及入队 token、人工覆盖、隔离/删除/黑名单。调用前再次核对授权；关闭后重新开启不会扩大旧队列权限。邮件已入库后处理，不把外部 AI 请求放进收件持久化事务。

处理流程：读有效缓存 → 必要时调用现有共享分析服务 → 验证结构与分类 → 原子保存自动值。分类写入比较完整的已保存分析快照，防止旧写入覆盖重新生成的新结果；后台快照变化时延后重读当前缓存。Telegram、网页与分类共用 claim，处理中的结果延后读取，避免并发重复计费。Telegram 遇到共享分析正在处理或 claim 忙碌时至少延后 5 秒，在后续调度读取结果；失败仍退回普通摘要。每个后台工作最多实际发起一次生成；崩溃后已发起的尝试不自动重发。未发起供应商请求的忙碌/限额/本轮预算耗尽可延后；调用前预算超时恢复未尝试状态，实际调用后超时不自动重试。供应商失败降级到规则。成功分析返回空建议时，原子清除旧 AI 分类并回到本地规则；人工覆盖和当前授权仍优先，失败分析不清除先前成功分类。模型自报 confidence 只作提示，不作为保证准确的阈值。

自动分类与手动生成、Telegram 共用现有 Owner 每小时 30 次限额，不擅自提高。积压不抢占无限运行时间；超过额度等待下一窗口。第一版不做自动历史回填、无限重试、自动标签、自定义规则编辑器、回复生成或附件分析。

## 数据迁移与发布边界

追加 0032 migration，新增六类人工/AI 字段、后台工作表、缓存成功时间；同步 schema.sql、schema version、契约及删除清理。空库、legacy fixture、31→32 数据保留与快照一致性均须验证。旧列保留；新应用要求完整新 schema，远程迁移和兼容桥接部署必须按生产清单单独规划、获得授权，不能声称支持未迁移数据库。旧应用只写原分类列，因此生产桥接不能仅放宽版本检查：需要迁移至切换期间的网页分类写入暂停，或明确双写新旧字段的桥接代码，防止迁移后旧写入遗漏。

不读取或复制私有配置/密钥，不部署生产、不写真实邮件或 Telegram。PRE 发布与独立 D1 迁移需要用户授权；所有可独立进行的本地实施、测试、提交与本地 review 先完成。功能 PR 必须在对应提交完成 PRE 页面/API 验收后创建；若尚未授权 PRE，保留提交与 worktree，报告明确门禁。

## 影响范围

- domain：分类枚举、旧 ID 规范化、规则、AI 输出与设置契约。
- server：设置授权、共享缓存保留、后台工作/dispatcher、入站入队、Cron、分类更新和邮件读取/过滤/计数/删除。
- UI：摘要默认展示、时间、重试；六类 tabs/批量菜单；自动分类设置及中英文文案。复用所有阅读入口的共享组件。
- data：顺序迁移、schema 快照、版本、测试 fixture。
- docs：AI/API/开发/Preview/生产及双语 README 的公开行为说明。
